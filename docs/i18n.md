# Internationalization (i18n)

muse uses [`next-intl`](https://next-intl.dev/) for UI translations.
Supported locales: **`en`** (default) and **`ja`**.

## Wiring

- `i18n/config.ts` — the framework-free source of truth for `locales`,
  `defaultLocale`, and the `NEXT_LOCALE` cookie name and lifetime.
- `i18n/routing.ts` — re-exports the locale constants and the typed `Link`,
  `redirect`, `usePathname`, `useRouter`, `getPathname` helpers from
  `createNavigation(routing)`. Use these helpers (not the raw Next.js ones)
  so locale prefixes are preserved. It also sets `localeCookie.maxAge`;
  without it next-intl writes `NEXT_LOCALE` as a session cookie and the
  redirects below forget the choice when the browser closes.
- `i18n/locale-redirects.ts` — generates the `redirects()` rules in
  `next.config.ts` that send prefix-less paths (`/`, `/canvas`, …) to a
  locale-prefixed URL: a `NEXT_LOCALE` cookie wins, then an
  `Accept-Language` header whose **first tag** is `ja`, then the default
  locale. This replaces the former next-intl proxy (middleware), which
  OpenNext cannot run. The header test is a first-tag match, not the
  proxy's q-value negotiation, so it can disagree with a browser that lists
  a third language first — the cookie corrects it from the next request on.
- `components/locale-cookie-sync.tsx` — writes `NEXT_LOCALE` from the URL
  locale on every localized page, the way the proxy's `syncCookie` did.
  Without it the cookie is only ever written by the language switcher, and
  a visitor who arrives on a shared `/ja/…` link is sent to `/en` the first
  time they follow a prefix-less URL.
- `lib/locale-alternates.ts` — builds the `alternates.languages` metadata
  each page needs. The proxy used to emit these as `Link: rel="alternate"`
  hreflang headers on every response; a new localized page has to declare
  them in its own `generateMetadata` or search engines see the locale
  variants as unrelated duplicates.
- `i18n/request.ts` — resolves the request locale, falls back to the
  default, and loads `messages/{locale}.json` dynamically.
- `messages/en.json`, `messages/ja.json` — translation dictionaries. Keys
  are shared 1:1 between the two files.
- `app/[lang]/…` — all user-facing routes live under a locale segment so
  the locale is part of the URL (e.g. `/en/canvas`, `/ja/evidence/08`).

## Agent output language

UI strings are translated via `next-intl`, but the backend agents emit
free-form content (logic-model cards, evidence reasoning, chat replies)
in the **user's input language**, independent of the URL locale. See
the `muse-backend` repository (`src/ai/prompts/`)
for the policy and which structured labels stay in English.

For external paper search, the backend's query translation agent is
the source of truth for detecting non-English input and translating it
into English keywords before hitting Semantic Scholar.

The **recipe workflow** is the one exception that takes the UI locale
directly: `/api/recipe/stream` forwards `locale: "en" | "ja"` from the
canvas page into the workflow, and the agent prompt is interpolated with
`"Write the recipe in English/Japanese"`. The locale knob exists because
the recipe is generated from card text that has already been normalised
on screen, so the user's URL locale is a more reliable signal than
guessing from short metric labels. See
the `muse-backend` repository (`src/ai/workflows/recipe.ts`)
for the surrounding contract.

## Adding a translation key

1. Add the key to both `messages/en.json` and `messages/ja.json`.
2. Use it in a server or client component via `useTranslations("namespace")`
   or `getTranslations` from `next-intl/server`.
3. Keep key names stable — they are the contract across locales.

## Adding a new locale

1. Add the code to `locales` in `i18n/config.ts` (`i18n/routing.ts` only
   re-exports it). The redirect rules and hreflang alternates are generated
   from that list, so both pick the new locale up automatically.
2. Create `messages/<locale>.json` with the same keys as `en.json`.
3. Add an `Accept-Language` rule for it in `i18n/locale-redirects.ts` if
   first-visit detection should work without a cookie — only `ja` has one,
   because every other header falls through to the default locale.
4. Optional: update any agent instructions that hard-code language
   examples (grep `messages/`, `config.ts`, and agent instructions files).

## Adding a localized page

Call `setRequestLocale(lang)` before any `getTranslations()` in the page
body. The layout calls it too, but layouts and pages render in parallel, so
the layout's call is not guaranteed to have populated the request cache
first — the page renders in the default locale when it loses that race.
Export a `generateMetadata` that returns `localeAlternates(lang, path)` so
the page declares its hreflang alternates.
