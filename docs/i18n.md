# Internationalization (i18n)

muse uses [`next-intl`](https://next-intl.dev/) for UI translations.
Supported locales: **`en`** (default) and **`ja`**.

## Wiring

- `i18n/config.ts` — the framework-free source of truth for `locales`,
  `defaultLocale`, and the `NEXT_LOCALE` cookie name.
- `i18n/routing.ts` — re-exports the locale constants and the typed `Link`,
  `redirect`, `usePathname`, `useRouter`, `getPathname` helpers from
  `createNavigation(routing)`. Use these helpers (not the raw Next.js ones)
  so locale prefixes are preserved.
- `i18n/locale-redirects.ts` — generates the `redirects()` rules in
  `next.config.ts` that send prefix-less paths (`/`, `/canvas`, …) to a
  locale-prefixed URL: an explicit `NEXT_LOCALE` cookie wins (written by the
  language switcher), then an `Accept-Language` header starting with `ja`,
  then the default locale. This replaces the former next-intl proxy
  (middleware), which OpenNext cannot run.
- `i18n/request.ts` — resolves the request locale, falls back to the
  default, and loads `messages/{locale}.json` dynamically.
- `messages/en.json`, `messages/ja.json` — translation dictionaries. Keys
  are shared 1:1 between the two files.
- `app/[lang]/…` — all user-facing routes live under a locale segment so
  the locale is part of the URL (e.g. `/en/canvas`, `/ja/evidence/08`).

## Agent output language

UI strings are translated via `next-intl`, but the backend agents emit
free-form content (logic-model cards, evidence reasoning, chat replies)
in the **user's input language**, independent of the URL locale. See
the `muse-backend` repository (`src/ai/prompts/`)
for the policy and which structured labels stay in English.

For external paper search, the backend's query translation agent is
the source of truth for detecting non-English input and translating it
into English keywords before hitting Semantic Scholar.

The **recipe workflow** is the one exception that takes the UI locale
directly: `/api/recipe/stream` forwards `locale: "en" | "ja"` from the
canvas page into the workflow, and the agent prompt is interpolated with
`"Write the recipe in English/Japanese"`. The locale knob exists because
the recipe is generated from card text that has already been normalised
on screen, so the user's URL locale is a more reliable signal than
guessing from short metric labels. See
the `muse-backend` repository (`src/ai/workflows/recipe.ts`)
for the surrounding contract.

## Adding a translation key

1. Add the key to both `messages/en.json` and `messages/ja.json`.
2. Use it in a server or client component via `useTranslations("namespace")`
   or `getTranslations` from `next-intl/server`.
3. Keep key names stable — they are the contract across locales.

## Adding a new locale

1. Add the code to `locales` in `i18n/routing.ts`.
2. Create `messages/<locale>.json` with the same keys as `en.json`.
3. Optional: update any agent instructions that hard-code language
   examples (grep `messages/`, `routing.ts`, and agent instructions files).
